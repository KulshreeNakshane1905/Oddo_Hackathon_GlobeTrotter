## Comprehensive Solution for GlobalTrotters Travel Planning Application

### 1. Introduction
GlobalTrotters is a multi‑city travel planning platform that empowers users to create, customize, and share complex itineraries. Our solution combines a robust relational database, a scalable backend API, and an intuitive, responsive frontend to deliver a seamless user experience. The design follows a modular approach, ensuring each feature is well‑integrated and can be independently evolved.

---

### 2. System Architecture
The application is built as a **three‑tier architecture**:
- **Frontend (Client)** – React (with TypeScript) for a dynamic, component‑based UI; state managed via Redux Toolkit.
- **Backend (Server)** – Node.js + Express providing RESTful APIs and business logic.
- **Database** – PostgreSQL (relational) to store user, trip, and activity data with full ACID compliance.
- **Additional Services**:
  - **Authentication**: JWT‑based with refresh tokens.
  - **File Storage**: Railway for cover photos and activity images.
  - **Caching**: Redis for frequent reads (city search, popular destinations) and session caching.
  - **Search**: PostgreSQL full‑text search or Elasticsearch for city/activity search.
  - **Charts/Reporting**: Server‑side aggregation + Chart.js on the frontend.

![High‑level architecture](https://via.placeholder.com/800x400?text=Architecture+Diagram)

**Data Flow**:
- User interacts with the frontend → API calls to backend → backend validates and interacts with the database → returns JSON responses → frontend updates UI.
- Public sharing generates a unique token and serves a read‑only version from the same backend.

### 3. Database Schema (Relational Design)
We define a clean, normalized schema with the following core tables:

| Table | Columns | Description |
|-------|---------|-------------|
| **users** | `id` (PK), `email`, `password_hash`, `full_name`, `profile_pic`, `language_pref`, `created_at`, `updated_at` | User accounts. |
| **trips** | `id` (PK), `user_id` (FK → users), `trip_name`, `description`, `start_date`, `end_date`, `cover_photo_url`, `is_public` (boolean), `share_token` (unique), `created_at`, `updated_at` | A trip belongs to one user. |
| **stops** | `id` (PK), `trip_id` (FK → trips), `city_id` (FK → cities), `order_index` (integer), `start_date` (date), `end_date` (date), `notes` (text), `created_at`, `updated_at` | Each trip has multiple stops; each stop references a city and has its own date range. |
| **cities** | `id` (PK), `name`, `country`, `country_code`, `cost_index` (decimal), `popularity_score` (integer), `latitude`, `longitude`, `timezone` | Pre‑loaded with data from an external source. |
| **activities** | `id` (PK), `city_id` (FK → cities) or `null` (global), `name`, `description`, `type` (enum: sightseeing, food, adventure, etc.), `avg_cost` (decimal), `duration_hours` (decimal), `image_url`, `created_at` | Master list of activities, optionally associated with a city. |
| **stop_activities** | `id` (PK), `stop_id` (FK → stops), `activity_id` (FK → activities), `scheduled_time` (timestamp), `cost` (decimal) – can override `avg_cost`, `notes` | Links activities to a specific stop, with a concrete time and cost. |
| **budget_estimates** | `id` (PK), `trip_id` (FK → trips), `total_transport` (decimal), `total_accommodation` (decimal), `total_activities` (decimal), `total_meals` (decimal), `total_other` (decimal), `currency` (varchar), `calculated_at` (timestamp) | Stores aggregated budget breakdown; could be recomputed on each change. |
| **shared_links** | `id` (PK), `trip_id` (FK → trips), `token` (unique), `expires_at` (timestamp) – if expiry needed | For managing public share tokens; we can also use `share_token` in trips table directly. |
| **user_saved_cities** | `id` (PK), `user_id` (FK → users), `city_id` (FK → cities) | (For profile – saved destinations) |

**Relationships**:
- A **User** has many **Trips**.
- A **Trip** has many **Stops** (ordered).
- A **Stop** belongs to one **City** and one **Trip**.
- A **Stop** has many **StopActivities**.
- An **Activity** can be used in many StopActivities (many‑to‑many through stop_activities).
- **Cities** can be pre‑populated from a curated dataset (e.g., GeoNames) with cost index and popularity.

**Indexes**: Foreign keys, `(trip_id, order_index)` on stops, `(user_id, created_at)` on trips, `city_name` for search, etc.

### 6. Feature Implementation Details

#### 6.1 Authentication & Security
- Passwords hashed using bcrypt.
- JWT with short expiration (15 min) and refresh token stored in an `httpOnly` secure cookie.
- Role‑based access control: `admin` flag in users table.
- Input sanitization and rate limiting.

#### 6.2 Itinerary Builder & Data Consistency
- When a trip’s `start_date` or `end_date` changes, the backend can optionally adjust stop dates proportionally (or warn the user).
- Stop dates must be within the trip’s date range; enforced on the backend.
- Reordering stops updates `order_index` and renumbers all stops in the trip.

#### 6.3 Budget Computation
- Budget is computed on‑demand from the database:
  - **Transport**: can be estimated based on distance between stops (using external API like Google Maps, but for MVP we may use a default cost per km or allow user input). Instead, we store a `transport_cost` per stop or per trip? To keep it simple, we can have a separate `transport_estimate` per stop (or trip) that the user can enter, or compute from city cost index.
  - **Accommodation**: could be estimated from city cost index and number of nights.
  - **Activities**: sum of `cost` from `stop_activities`.
  - **Meals**: estimated from city cost index * (number of days * meals per day).
- These are just estimates; we can also allow users to override each category directly in the UI.
- The budget endpoint returns a breakdown and highlights “over‑budget” days if the user sets a daily budget (stored in trip table).

#### 6.4 Search Performance
- PostgreSQL full‑text search with trigram indexes on city names and activity names.
- For larger datasets, we can add Elasticsearch, but for hackathon scale, PG search is sufficient.
- Filters (country, type, cost) are applied via SQL `WHERE` clauses.

#### 6.5 Sharing Public Itinerary
- When user toggles `is_public` or clicks “Generate Share Link”, a unique `share_token` (UUID) is generated and stored in the trips table.
- The public endpoint `/api/public/trip/:token` returns the trip data **without** exposing user details or editing options.
- “Copy Trip” – for authenticated users, a new trip is created by duplicating all stops and activities; the user becomes the owner.

#### 6.6 Admin Analytics
- Aggregated queries on the database (e.g., `COUNT(*) FROM trips GROUP BY DATE(created_at)`, top cities by stop count, top activities).
- Provide this data via an admin API endpoint, and render charts on a protected admin page.

### 7. Data Flow Example: Creating a Trip
1. User fills “Create Trip” form → POST `/api/trips` → backend inserts into `trips` → returns trip ID.
2. User navigates to Itinerary Builder for that trip → GET `/api/trips/:id` fetches trip with stops and activities.
3. User adds a stop → selects a city from search → POST `/api/trips/:id/stops` → backend inserts into `stops`, and if city does not exist, it can be created on‑the‑fly (but we pre‑populate cities).
4. User adds an activity to that stop → POST `/api/trips/:id/stops/:stopId/activities` → inserts into `stop_activities`.
5. User edits dates or reorders stops → PUT `/api/stops/:id` updates order and dates.
6. User views budget → GET `/api/trips/:id/budget` → backend calculates and returns JSON.
7. User shares trip → POST `/api/trips/:id/share` → generates token, sets `is_public=true`, returns shareable URL.

## How Supabase Simplifies Your Architecture

1. **Authentication**  
   Instead of rolling your own JWT + bcrypt, you can use Supabase Auth (built on GoTrue). It provides email/password login, signup, password reset, and session management out‑of‑the‑box.  
   - Your frontend calls `supabase.auth.signUp()` / `signIn()`.  
   - The Supabase client handles token refresh automatically.  
   - Backend can still validate the JWT via Supabase’s `verify` method.

2. **Database (PostgreSQL)**  
   Your schema (users, trips, stops, etc.) maps 1:1 to Supabase tables.  
   - **Row Level Security (RLS)** – you can enforce that users can only see/modify their own trips directly in the database, adding an extra security layer.  
   - **Real‑time subscriptions** – if you want live updates when a shared itinerary is viewed or when activities are reordered, Supabase’s `realtime` feature is built‑in.

3. **API Generation**  
   Supabase auto‑generates REST endpoints for each table. For hackathon speed, you can even bypass Express for simple CRUD and only write custom endpoints (budget calculations, sharing, admin stats) in Node.js. But I’d recommend keeping your Express layer as an orchestration middleman to handle complex business logic and external API calls.
